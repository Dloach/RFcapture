# 固件调试与自动取证方法（开发要求）

> 任何继续开发本固件的人（包括 AI 助手）**先读这一篇**。它规定了我们定位硬件/固件
> 问题的标准做法。这套方法在 2026-11-15 定位了 HARNESS 语音卡顿的真正根因——此前
> 另一条调试路线（deepseek）让用户反复手动测试几十轮仍未找到病根，差别不在智力，
> 而在**流程**：是测量还是猜测，证据是否自动留存，是否验证继承来的诊断。

## 0. 三条铁律

1. **测量，不要猜测。** 每一个「可能是 X 坏了」都必须有一个能产出数字的实验支撑。
   没有数字之前，不写修复代码，不下结论。
2. **证据由设备自己自动持久化，并有一条不需要用户操作的读回路径。** 不要请用户
   「再按一次 / 再说一句 / 再贴一张卡」来补数据。台架设备可能离宿主很远，重做的成本
   是走路而不是敲键盘——方案不能默认用户随时在场、随时能重做。
3. **继承来的诊断必须先验证再信。** 文档里、上一轮会话里、别的 AI 给出的结论，都是
   *待验证的假设*，不是事实。本案里「I2S 时钟慢 16 倍 / ES8311 是时钟主机」就是未经验证
   被当成事实，把几十轮调试带进死胡同。

## 1. 标准闭环

每一轮迭代都走完整闭环，而不是「改代码 → 让用户试 → 听用户描述」：

1. **让设备自己取证。** 写一个自检（self-test），开机即跑、**无需说话/按键/贴卡**。
   本案的 `voiceSelfTest()`（`src/harness_app.cpp`）用纯阻塞 `i2s_read` 测真实硬件
   采样率，不需要任何用户输入。
2. **隔离变量。** 把「硬件本身」和「软件循环」分开测：
   - 纯读自检（无 render、无 WS 发送、无键盘扫描）→ 硬件真实速率 `voiceHwHz`。
   - 完整采集循环 → 端到端吞吐 `voiceMeasuredHz`。
   两者一比较，立刻知道问题在硬件还是在循环。本案 `hw=16000` 而循环只有 `767Hz`，
   一句话就把「时钟慢」的假设证伪了。
3. **逐阶段计时。** 在循环里给每个阶段单独打时间戳：`read / send / render / update`。
   本案正是 `read=237ms send=4767ms` 这一行，直接指出瓶颈是 **WS 发送**，不是采集。
4. **诚实的指标。** 吞吐 = **实际发送出去的样本数 / 墙钟时间**，不是「请求的块大小 ×
   次数」。partial read 意味着 DMA 溢出丢了样，必须如实计入，否则指标会骗人。
5. **单变量改动 → 自动烧录 → 自动抓串口 → 对比数字。** 一次只改一个地方，烧录后
   自动抓串口日志，用数字确认改动有效，再进下一轮。不靠用户口头反馈判断成败。

## 2. 证据落盘与读回（铁律 2 的具体要求）

- **持久化：** 关键结果写 NVS（片上 flash 兜底）或 SD（优先）。本案 `voiceHwHz` 写进
  NVS `harness/hwHz`，掉电不丢。每条记录 open/append/close——台架设备随时可能被拔电，
  长期持有句柄会丢掉最后一次 flush 之后的数据。
- **无需用户操作的读回：** 用**周期性日志整份回灌**，不要靠按键触发，也不要只在开机
  那一刻 dump（设备一上电就启动，那时宿主还没打开 CDC 口，dump 会丢）。本案每 5s 的
  `[mem] ... hw=%u` 行随时把自检结果带出来，抓任何一段串口都能读到。
- **同时上设备屏幕：** 证据不能只在宿主串口里。本案屏幕右上角常驻 `H16k`（硬件速率），
  电平条显示麦克风是否在听——不接串口也能判断状态。
- **成功和失败都记，不去重：** 失败样本同样是证据。需要合并时记一个间隔字段，让离线
  合并成为可能，而不是在设备端去重把真实发生的事抹掉。
- **别用已知有问题的输入路径触发读回：** 例如键盘曾有未定案的卡死，自检就不该依赖按键。

## 3. 工具链

- **镜像构建 `tools/harness-build.ps1`：** 项目放在 SMB 共享（`Y:`）上，共享会报零长
  文件 / 过期元数据，直接让 PlatformIO 的 LDF 卡死。脚本把 `src/boards/platformio.ini`
  镜像到本地盘再编译，约 45s。`-Upload -Port COM13` 编译并烧录。
- **自动重连抓串口 `tools/cap-serial.py`：** 板子每次复位都会重新枚举 USB-CDC 口，
  普通 `pio device monitor` 恰好在最关键的开机段断掉。这个脚本自动重开端口、过滤噪声、
  带时间戳落盘。用 PlatformIO 自带解释器跑（系统 python 可能缺 pyserial）：
  `%USERPROFILE%\.platformio\penv\Scripts\python.exe tools/cap-serial.py 30`
- **USB 日志 `src/usb_log.h` / `usbLogf`：** 本固件 `Serial` 是 UART0，没接到 USB；
  应用日志走 main.cpp 里共享的 USBCDC（`usbSerial`）。端口在 `USB.begin()` 之后才存在，
  所以从 `loop()` 打日志，别在 `setup()` 早期打。

## 4. 反模式（本案真实踩过的坑）

- **把循环吞吐当成硬件时钟。** 采集循环被发送阻塞 → 测出 767Hz → 误判「I2S 时钟慢
  16 倍」。真相：硬件纯读 16000Hz 完全正常，慢的是被 WS 发送拖垮的循环。
- **继承未验证的诊断。** 「ES8311 是时钟主机」被写进文档当真，于是去「自己从头写 I2S
  驱动」这种 driver 级大工程。实际寄存器 `0x01=0xBA`（MCLK=BCLK）证明它是**从机**，
  直接读 M5Unified 装好的通道就有真实音频，根本不用重写驱动。
- **依赖用户反复手动测试。** 让用户「再说一句」几十轮，每轮只拿到模糊的口头反馈，
  没有可对比的数字，永远在原地打转。
- **证据只打串口、不落盘。** 抓取窗口一关数据就永久丢失，只能请用户重做。
- **小写阻塞误判为网络/硬件问题。** `sendFrame` 把一帧切成 80 个 128 字节小包逐个
  `write`，超过 lwIP 发送缓冲后每个小包等延迟 ACK，一帧阻塞 ~4.8s。改成整帧单次
  `write` 后降到 ~24ms。瓶颈在发送策略，不在时钟、不在麦克风。

## 5. 案例复盘：HARNESS 语音卡顿（2026-11-15）

证据链（全部来自设备自动取证，无一次要求用户重说）：

| 实验 | 数字 | 结论 |
|---|---|---|
| 纯读自检 `voiceSelfTest` | `hw=16000Hz`，ES8311 `01=BA` | 硬件时钟正常，codec 是从机 → 证伪「16× 慢 / 主机」 |
| 采集循环逐阶段计时 | `read=237ms send=4767ms` | 瓶颈是 WS 发送，不是采集 |
| 改整帧单次 `write` 后 | `send≈24ms`，`measured=14837Hz` | 发送修复，吞吐恢复 |
| 加深 RX DMA（12×256）后 | `measured=15921Hz`，`min heap=24748B` | 接近实时，长采集不丢样，堆余量安全 |

修复要点：整帧掩码后单次 `socket_.write()`；掩码缓冲用**静态数组**而非 `malloc`
（堆碎片化时 free=76KB 也分配不出 10KB 连续块）；自检先排 DMA 积压再测稳态速率
（否则积压把读数抬高到 ~17.5kHz，造成「采样率偏差」的假象）。

## 6. 宣称「修好了」之前的检查清单

- [ ] 有一个**无需用户操作**即可复现/取证的实验，且结果自动落盘 + 周期回灌 + 上屏。
- [ ] 关键假设都用数字验证过，尤其是继承来的诊断。
- [ ] 瓶颈定位到具体阶段（有逐阶段计时），不是「大概网络/硬件问题」。
- [ ] 指标诚实（实际产出 / 墙钟），失败样本也记录。
- [ ] 单变量改动，烧录后自动抓串口对比过数字，无回归（其它功能日志正常）。
- [ ] 公开仓库：提交前扫过真实凭据 / 卡 UID / 遥控码（见 `docs/README.md`）。
