### 0.2 对审查判断的三处修正

1. **测试不是“从没通过”，而是“没有在本机重新编译过”**。
   旧 exe 时间戳 11-08、源码 11-09，确实只覆盖了 12 项；但用 WSL 的 g++ 15.2
   重新编译当前源码后，25 项全部通过（含 `estimateBaseUs` / `scoreWaveform`）。
   所以 P2 的重点是“让本机能一键重编”，不是修测试。
2. **RMT 截断不能只改 `clk_div`**。
   解码器允许 T 到 2000 µs（31T ≈ 62 ms），但接收侧 `RF_FRAME_GAP_US=18000`
   会在 T > 580 µs 时把 31T 同步低电平当成帧间隔。只把发送改成 2 µs/tick，
   会得到“发得出去、采不回来”的假支持。正确做法是先定支持包络（见 P2-2）。
3. **RF 快捷绑定也有同类“下标失效”问题，只是不取模**。
   `src/launcher.cpp:69` 只检查 `b.index >= saved.size()`：删掉前面的信号后，
   下标仍在范围内，会**静默发另一条信号**。NFC 的取模更糟，但两者要一起修（P0-1）。

### P0-1 快捷绑定改成“稳定身份”，越界/失效必须显式报错

**现状**

- `quickbind::Binding` 只有 `index`（`src/quick_bind.h:17-22`），指向 `SavedStore` 或
  `nfccards` 的数组下标。
- 删卡/删信号/从 TF 恢复都会让下标平移；NFC 用 `idx % count` 兜底，结果**静默模拟另一张卡**；
  RF 只挡“越界”，下标仍在范围内时会**静默发另一条信号**。
- 对开门工具，“发错”比“不发”危险得多。

**改法**

1. `Binding` 增加 `uint32_t key`，文件格式从 5 字段扩成 6 字段：
   `slot;kind;index;icon;color;key`。旧文件只有 5 字段时 key 默认 0，仍能读。
2. `quick_bind.h` 里加纯函数（便于 host 测试）：
   - `keyForNfc(const uint8_t* uid, uint8_t len)`：FNV-1a over UID，返回非 0。
   - `keyForRf(uint8_t band, bool decoded, uint32_t code, uint8_t bits,
     const uint16_t* pulses, int count)`：
     - `decoded == true`：对 band / bits / code 做 FNV-1a，结果置最高位；
       **code 可以为 0**（EV1527 全 0 是合法码），所以不能拿 `code != 0` 当有效判据；
       `bits` 要进 key，否则 EV1527（24 bit）和 PT2262（12 symbol）同值同频段会撞。
     - RAW：对 `count` 和每个脉宽做 FNV-1a，清掉最高位，保证非 0。
3. 绑定时把 key 一起写入：`bindpick::run(...)`、`quickbind::set(...)` 增加 key 参数；
   RF 在 `src/app.cpp` 绑定处算，NFC 在 `src/nfc_app.cpp` 绑定处算。
4. 执行时按 key 解析，**不再取模**：
   - RF：在 `SavedStore` 里找 `keyForRf(...) == b.key` 的条目；找不到再允许
     `b.key == 0 && b.index < saved.size()` 的旧绑定；仍找不到就提示
     `BINDING STALE`，不发送。
   - NFC：`queueEmulation(idx, key)` 把 key 一起写进 `nfcretry` NVS（`Boot` 结构加
     `uint32_t key`，`clearBoot()` 同步 `remove("key")`）；
     `emulatorSetup` 加载卡后按 key 找；找不到或 `!replayable` 就
     `emuFail("BINDING STALE")`。旧绑定 key=0 时按 index，但仍做
     `idx < count && replayable` 校验，绝不取模。
5. 旧绑定迁移：key=0 且 index 成功解析时，把算出的 key 回填到该 slot 并保存
   （RF 在 launcher 可直接做；NFC 在模拟页启动时通过 `quickbind` 回填，
   或至少在新绑定时写入）。**不要求**一次把所有旧绑定修对；升级后建议重新绑一次。

**涉及文件**

`src/quick_bind.{h,cpp}`、`src/bind_picker.cpp`、`src/app.cpp`、`src/launcher.cpp`、
`src/nfc_app.{h,cpp}`。

**验收**

- 绑定 NFC 第 2 张卡 → 删除第 1 张 → 按快捷键：要么模拟原第 2 张，要么显示
  `BINDING STALE`；**不能**模拟成第 1 张。
- 绑定 RF 第 2 条 → 删除第 1 条 → 按快捷键：要么发原第 2 条，要么报错；不能发第 1 条。
- 从 TF 恢复后卡/信号顺序变化，再按快捷键，行为同上。
- 旧 `/quick.txt`（5 字段）能加载，旧绑定不崩溃。
- host 测试覆盖 `keyForRf` / `keyForNfc` 的稳定性（同码不同波形 key 相同；
  不同 band/不同 UID key 不同；RAW 不同波形 key 不同）。

**如果时间不够的热修**

只做边界校验，不做 key：

```cpp
// NFC
if (idx >= nfccards::count || !nfccards::replayable(nfccards::cards[idx])) {
    emuFail("BINDING STALE");
}
emuIdx = idx;

// RF
if (b.index >= saved.size()) { /* toast BINDING STALE */ }
```

这能挡住“越界取模”，但挡不住“下标平移后仍在范围内”的静默错发。
所以热修只能作为过渡，**P0-1 的 key 方案仍要做**。

预计：1.5–2 h（含 host 测试）。

### P0-2 永久保存：按“blob 先写、count 后写”提交，并能从字节数自愈

**现状**

`src/saved_store.cpp:44-55`：

1. 写 `magic`
2. 写 `count`
3. 写 `items`

`begin()` 要求 `bytes == sizeof(SavedSignal) * stored` **精确相等**，否则整份列表归零。
如果掉电发生在 2 和 3 之间，count 已经是新值、blob 还是旧的，恢复直接判坏——
永久保存的列表比采集列表更脆弱，而它才是不可再生的那份。

**改法**

1. `save()` 顺序改成：
   - 先写 `magic`
   - 再写 `items`（`count_ > 0` 时）；`count_ == 0` 时 `prefs.remove("items")`
   - **最后**写 `count`（提交位）
2. `begin()` 自愈，照搬 `CaptureStore::begin()` 的思路：
   - `magic` 必须对；
   - 恢复算法抽成 `saved_store.h::recoverSavedCount()`，便于 host 测试；
   - `stored <= 0` 视为空列表（防止旧固件“清空只写 count”留下的 blob 复活）；
   - `bytes` 足够覆盖 `stored` 条完整记录时，以 `stored` 为准（忽略未提交的尾部）；
   - `bytes` 不足 `stored` 条时，按完整记录数向下取整，尽量保住前缀；
   - 结果 clamp 到 `rfcfg::maxSaved`。
3. 加一行日志，和 CaptureStore 对齐：
   `[saved] restored n=%d magic=0x%04X count=%d bytes=%u`。
4. `replaceAll()` 仍走 `save()`，不要另写一套。
5. `SavedStore::add()` 里把 `s.count` clamp 到 `rfcfg::storedPulses`（防御性，正常路径不会超）。
6. 这仍然不是事务性的：如果要求“任何时刻掉电都不丢”，下一步是双槽 A/B（两份 blob +
   序号），代价是 NVS 写放大。本轮先做提交顺序 + 字节自愈，能消掉“count 新、blob 旧”
   这个最致命的窗口。

**涉及文件**

`src/saved_store.cpp`、`src/saved_store.h`（如果暴露恢复 helper 给 host 测试）。

**验收**

- 正常：保存 3 条 → 删除 1 条 → 重启，剩 2 条且名字/波形正确。
- 模拟撕裂（建议加一个仅测试用的 `RF_TEST_TORN_SAVE` 编译开关，写到 items 后直接
  `ESP.restart()`，不写 count）：重启后至少保留旧列表的前缀，不能整份归零。
- 空列表：清空 → 重启，不能复活。
- 先 `BACKUP TO TF` 再做任何掉电测试；测试完能恢复。

预计：0.5–1 h + 上机。

### P0-3 同码值重采时，用更好的波形替换坏波形

**现状**

`src/capture_store.cpp:139-148`：同 band + 同 code（或 RAW 的 `similarTrain`）只
`hits++`，不替换 `pulses`、不更新 `quality_`。README 让用户“q40 以下删掉重采”，
但用户最自然的动作是直接再按一次遥控器——结果什么也没改善。

**改法**

1. 抽一个纯策略函数（放 `capture_store.cpp` 的匿名 namespace 或小头文件，便于 host 测试）：

   ```cpp
   bool shouldReplaceWaveform(uint8_t oldQ, uint8_t newQ) {
       if (oldQ == 0) return newQ > 0;
       if (oldQ < 40 && newQ >= 60) return true;
       return newQ >= oldQ + 10;
   }
   ```

   阈值 10 分是经验值：避免每次抖动都重写 NVS；`oldQ < 40` 时给一次“救回来”的机会。

2. `CaptureStore::ingest()` 命中同一条时：
   - 先算新波形的 `scoreOf(train)`；
   - 满足 `shouldReplaceWaveform` 才复制 `pulses/baseUs/count/bits/proto/valid`，
     保留 `hits`/`band`/`code`；
   - 更新 `quality_[i]`，立即 `save()`（这是用户可见的改善，不能等 30 s flush）；
   - 通过新增的 `bool* improved` 出参告诉调用方，`src/app.cpp:701-723` 弹
     `BETTER WAVE` 或类似提示，而不是只对 `isNew` 响。
3. `SavedStore::add()` 同样处理重复项：
   - 现在返回 `bool`，改成 `enum class AddResult { kAdded, kDuplicate, kUpdated, kFull }`；
   - 重复且新波形更好时，复制新波形并保留 `name`，`save()`，返回 `kUpdated`；
   - `src/app.cpp::confirmSave()` 按结果提示 `SAVED` / `ALREADY SAVED` / `WAVEFORM UPDATED` /
     `SAVE LIST FULL`。
4. 不自动把采集列表的改善同步到永久列表：用户再按一次 `ENTER` 保存即可
   （现在会走 `kUpdated`，不会再只提示 `ALREADY SAVED`）。这样不会在用户不知情时
   改掉永久记录。

**涉及文件**

`src/capture_store.{h,cpp}`、`src/saved_store.{h,cpp}`、`src/app.cpp`。

**验收**

- 先采到一条 q30 的同码记录，再从更好位置重采到 q90：
  采集列表的 q 值变成 90，hits 继续累加，没有新增重复行。
- 在发送页对同一条再按 `ENTER`：永久列表的 q 值也变成 90，名字不变，不新增记录。
- q90 的记录被 q85 的重复采集覆盖时**不**替换（阈值保护）。
- host 测试覆盖 `shouldReplaceWaveform` 的边界（0、39、40、60、+10）。

预计：1–1.5 h + 上机。

### P1-5 NFC 命中计数改成批量写，且不要在射频场打开时写 flash

**现状**

`src/nfc_cards.cpp:227-252`：每次 `add()` 命中都 `save()`；`save()` 是
tmp→bak→rename 的整文件重写。扫描时卡贴着每 400 ms 命中一次，就是每 400 ms
写一次 SPIFFS；而且 `scanOnce()` 在 `fieldOn()` 期间调用 `add()`
（`src/nfc_app.cpp:311-341`），等于一边辐射 13.56 MHz 一边写 flash。

**改法**

1. `nfccards` 增加 `bool dirty_`、`uint32_t lastFlushMs_`。
2. `add()`：
   - 已有卡：只 `++hits`、`dirty_ = true`，不 `save()`；
   - 新卡：写入数组、`dirty_ = true`，通过 `bool* isNew` 告诉调用方；
   - 不在 `add()` 里写文件。
3. 新增 `void flush(bool force = false)`：
   - `!dirty_` 直接返回；
   - 非 force 时 `millis() - lastFlushMs_ < 30000` 返回；
   - `save()` 成功后清 dirty、更新 `lastFlushMs_`。
4. `scanOnce()` 把 `add()` 收集完、`fieldOff()` 之后：
   - 有新卡 → `flush(true)`（新卡只发生一次，值得立即落盘）；
   - 只有命中 → `flush(false)`（最多 30 s 写一次）。
5. `readerLoop()` 每轮调 `flush(false)`；离开 NFC 功能、`rebootAs()` 前调
   `flush(true)`，避免丢最后几次计数。
6. `remove()` / `rename()` 仍立即 `save()`（用户显式操作，频率低）。

**验收**

- 一张卡贴着扫 10 s：SPIFFS 写入不超过 2 次（首次新卡 + 至多一次 30 s flush），
  `hits` 在退出前落盘。
- 扫描期间不再出现 `fieldOn()` 内写 flash。
- 断电后已落盘的 hits 还在；最多丢最后 30 s 的计数（可接受，和 RF 侧一致）。

### P2-2 RMT 慢脉宽：先定包络，再决定改法

**事实**

- `src/ook_tx.cpp:22-34`：1 µs/tick，duration 15 位，最大 32767 µs；
- 解码器 `src/ook_decoder.cpp:181-182` 允许 T 到 2000 µs（31T = 62 ms）；
- 接收侧 `src/rf_config.h:44-46` 的 `RF_FRAME_GAP_US=18000` 会在低电平 ≥18 ms 时切帧，
  所以 **T > 580 µs 的 31T 同步头在接收侧就已经被当成帧间隔**；
- 因此“T>1057 µs 发送被截断”是真的，但**不是唯一瓶颈**。

**做法（按需求选一条）**

- **A. 只修发送截断（低风险，推荐先做）**
  - 抽 `pickClockDiv(maxUs)`：`maxUs <= 32767` 用 80，否则用 160（2 µs/tick，
    最大 65534 µs）；
  - `sendRmt()` 发送前算整条 train 的最大 duration（含 `low + gapUs`），
    `rmt_set_clk_div()` 切到合适的 div，再 `rmt_write_items()`；
  - `clampTicks()` 按当前 div 计算上限，并把所有 duration clamp 到 `[1, 32767]`
    （2 µs/tick 下 1 µs 的窄脉冲会算成 0 tick，0 会终止 RMT 流）；
    日志里打一行 `[tx] div=160 maxUs=...`；
  - 这样不改变正常遥控器的 1 µs 精度，只让超长脉冲不再被削平。
- **B. 端到端支持慢遥控器（工作量大，先有样机再立项）**
  - 把 `RF_FRAME_GAP_US` 提高到 >62 ms（例如 65000），让 31T 同步不被切帧；
  - 验证背靠背快速遥控器不会因此合并出问题；
  - 加 host 测试 + 上机用真实慢遥控器验证采集/解码/回放；
  - 更新 README/DEV-STATE 的“支持 T 范围”。
- **C. 不改代码，只把话说清楚**
  - 在 README 写明“当前设计包络 T≈250–580 µs；更慢的遥控器可能采不到”；
  - 解码器的 2000 µs 上限只是同步候选的门限，不代表端到端支持。

**建议**：先做 A（避免已有采集被截断），同时把 C 写进文档；B 等到有真实慢遥控器
再立项。不要在没上机验证前把 `RF_FRAME_GAP_US` 改大。
